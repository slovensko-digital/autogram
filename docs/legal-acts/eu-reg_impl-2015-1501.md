# Commission Implementing Regulation (EU) 2015/1501 — eID interoperability framework

## Executive summary

This act governs **notified electronic identification schemes, cross-border authentication nodes and their operators**, not local electronic-signature creation or validation. Under the scope and organisational facts in the [register README](README.md), no direct duty on the Autogram desktop application, local API, CLI or publisher is established. In particular, an API listening locally is not thereby an eIDAS node; possession of an eID signing certificate does not make a file-signing application an operator of a notified identification scheme.

The principal duties concern node connectivity, message formats, confidentiality, incident records, security assurance and identity attributes. Member States, the Commission and the Cooperation Network also have mapping, specification-development and dispute-resolution responsibilities. They must not be turned into an independent signature-software vendor's implementation deadlines.

**Indirect relevance is separated below:** the definitions and identity-data model provide context if a future integration consumes cross-border eID authentication. That is not evidence that Autogram currently implements such an integration, nor an obligation to add one. Whether the application is an end-user product used in providing an eID/trust service remains Unknown under the shared facts; the separate question under eIDAS Article 15 is not resolved by this act.

Assessment/source-access date: **8 October 2026**; repository baseline: **5ca91d5c**. All rows are contextual or scoped out; none establishes Done or Not done. The complete original English text and the 2016 correction were obtained through public-authority reproductions and cross-checked. **Direct EUR-Lex text/metadata retrieval was unavailable**, so the absence of subsequent amendments/repeal through the assessment date is not conclusively verified. This is a reading aid, not legal advice or certification.

## Provision-by-provision assessment

The tables paraphrase requirements in English without reproducing the complete legal text. **None / Ignored** means the identified addressee or activity lies outside established scope, not that an applicable requirement may be disregarded. **Indirect / Ignored** identifies interpretative or possible integration context only. Source references below mean the obtained complete texts identified above. Evidence codes keep missing organisational evidence explicit rather than attaching unrelated Java files:

- **S** — shared scope in [README](README.md): local signing application/publisher; no established notified-scheme or cross-border-node role. Reassessment would require a notified-scheme notification, node-operator appointment or service agreement and deployment architecture showing the organisation's precise role.
- **N** — if node operation were established: node interoperability/conformance results, authentication-message captures, metadata configuration, security assessment/certification, incident-log design and applicable national retention rules; none was supplied or assessed.
- **I** — if eID authentication inputs were consumed: an integration specification, attribute schema/mapping and tests showing identity/representation/assurance handling; not established for current scope.
- **G** — governmental/Cooperation Network responsibility: relevant notification, opinion, specification, reference implementation or dispute record, not application source code.
