# Slovakia — Decree 78/2020 Coll. on public-administration IT standards

## Executive summary

**Assessment: 8 October 2026; repository baseline: `5ca91d5c`.** This decree principally regulates Slovak public-administration IT and its responsible authorities, not every independent publisher of desktop signing software. Autogram's desktop, local API and CLI nevertheless encounter its prescribed document formats, electronic forms and XMLDataContainer (XDC) structures. An authority deploying or procuring Autogram may need contractual and deployment-specific compliance evidence. No such contract, public-administration role or receiving-system approval was inspected.

The current official temporal version is **effective from 15 May 2026**, incorporating **82/2026 Coll.**, not the July 2024 consolidation. Some new data-model/form requirements have **1 January 2027** transitional dates; certain existing public APIs have **1 January 2029**. These are not established general deadlines for this publisher.

Inspected code builds XDC, distinguishes embedded from referenced schemas, records schema digests, and reads presentation metadata. It proves particular implementation choices, **not universal conformity with the current decree, every published form, all permitted container versions, every signature profile, or receiving-authority acceptance**. In particular, an XDC namespace ending `/1.1` is not proof of the form-publication ZIP container version `1.1` or `1.2`.

**Coverage warning:** this is an incomplete reading-register entry. The complete official consolidated HTML and all eight PDF-only annexes were obtained, but the tables below do not yet enumerate every subunit of the general provisions and every annex. The exact remaining coverage is identified at the end. It must not be represented as the requested exhaustive assessment or as legal advice/certification.

### Inspected implementation evidence

These evidence keys are used in the tables, rather than attaching unrelated Java code to public-authority governance duties.

- **B — builder:** [`XDCBuilder`](../../src/main/java/digital/slovensko/autogram/core/eforms/xdc/XDCBuilder.java), `transform`, lines 35–62; `createXMLData`, lines 102–111; referenced schemas, lines 114–126 and 142–169; embedded schemas, lines 129–139 and 172–195; digest OID representation, lines 198–200. It sets XML content type and generates `.xdcf`, embeds or references schemas, and stores presentation attributes. Version is derived from the identifier suffix with fallback `1.0`; this is not a general form-version correctness proof.
- **U — utility:** [`EFormUtils`](../../src/main/java/digital/slovensko/autogram/core/eforms/EFormUtils.java), constants lines 53–60; `extractTransformationOutputMimeTypeString`, lines 63–104; `computeDigest`, lines 106–115; `getXsltParamsFromXsltReference`, lines 169–193; `getFormUri`, lines 195–223; `transform`, lines 300–324; `fillXsltParams`, lines 326–350. The code establishes UTF-8, XDC namespace `/1.1`, selected HTML/TXT/XHTML recognition and canonicalized Base64 digest construction, but not all possible transformations or all legal profiles.
- **R — resource retrieval:** [`UpvsEFormResources`](../../src/main/java/digital/slovensko/autogram/core/eforms/UpvsEFormResources.java), constructor lines 18–29; `findResources`, lines 35–78. Reads `urn:manifest:1.0` entries from the UPVS dataset, selects a transformation, and compares SHA-256 digests when supplied. This is evidence of a particular retrieval path, not proof of support for all publication-container versions or all allowed hash algorithms.
- **M — MIME:** [`AutogramMimeType`](../../src/main/java/digital/slovensko/autogram/core/dto/AutogramMimeType.java), constants lines 12–15 and recognizers lines 37–58. XDC with/without `charset=UTF-8`, PDF, text, ASiC-E and PNG/JPEG are recognized there. Do not infer mandatory receipt of every decree format from these recognizers.
- **P — parameters:** [`SigningParameters`](../../src/main/java/digital/slovensko/autogram/core/SigningParameters.java), lines 49–63 and 78–113. Configurable signature form/container, SHA-256 default, canonicalization defaults and a PDF/A-check flag; neither setting a flag nor referencing DSS proves PDF/A/ETSI conformity.
- **PA — role boundary / organisational evidence:** confirmed independent desktop/local-API/CLI scope in [the register](README.md), not an established `orgán riadenia`, portal/access-point operator, form publisher, public cloud provider or designated reference validator. If commissioned/deployed as public-administration IT, obtain the authority's role decision, procurement/support contract, deployment architecture, published technical profile and acceptance-test report. No general publisher duty is inferred.
- **F — form interoperability evidence still needed:** specific published form package and version, `meta.xml`, manifest, XSD, all supported signing presentations, receiving-authority profile, current central metainformation-system validators and an end-to-end acceptance/visualization test. B/U/R establish only part of this evidence.
